# PetCare clinic onboarding MVP

This branch adds the first end-to-end PetCare-managed veterinary clinic workflow. It does not change external 2GIS search or payment processing.

## Browser routes

- `/clinic`: Signed-in clinic manager registration, review status, service configuration and appointment decisions.
- `/nearby/our/veterinary`: Public directory of approved PetCare clinics, appointment requests and the signed-in pet owner's requests.
- `/admin`: New **Clinics** review section, accessible only to a Firebase user with the existing `petcareAdmin` custom claim.
- `/nearby/veterinary`: Existing external 2GIS directory; those entries cannot receive PetCare bookings.

## Backend

Routes are registered in `admin-backend/render-api/clinics.cjs` by the existing Express/Firebase Admin API.

1. A Firebase-authenticated manager can save and resume a draft, upload the three required verification documents and submit clinic information.
2. Before upload, the manager must accept the versioned privacy notice. The backend records the consent version, UID and timestamp and audits acceptance; the wording is explicitly marked as pending legal review.
3. The backend accepts one PDF, JPEG or PNG per authenticated multipart request, checks its signature and enforces a 5 MiB limit. Object names are generated by the backend. Emulator fixtures use a separate in-process test provider; production references and metadata are stored in Firestore while document bytes use the private Supabase bucket.
4. Only an authorized PetCare administrator can view submitted application metadata and retrieve documents through the authenticated API. The API streams bytes with `no-store`; it does not return public or signed URLs. Admin metadata/document views and manager upload/replacement/deletion are audited without storing document bytes or object paths in audit events.
5. Pending and rejected clinics never appear in the directory and cannot receive appointments. An approved manager can edit public profile fields, configure working days and hours, and enable or disable services.
6. A signed-in pet owner can request an appointment only for a pet held under their own server-side Firebase UID namespace. Requests start as `pending`, carry an idempotency key and appear in the Pet Owner's clinic appointments.
7. The clinic manager confirms or rejects a request. Confirmation reserves a duration-aware time slot transactionally; the API rejects overlapping confirmed appointments. The owner can cancel their own pending or confirmed appointments and sees rejection feedback.

The MVP uses one independent clinic branch per manager account, with no Organization Owner role. One account can still be both a Pet Owner and Clinic Manager.

## Local setup

1. Use the existing `.env.emulator.local` and `npm.cmd run dev:emulators` for synthetic Firebase data; do not overwrite existing environment files.
2. The backend-only `admin-backend/render-api/.env.supabase.local` is ignored by Git and loaded by its local `dev` and `dev:emulator` scripts. It contains empty placeholders for `SUPABASE_URL` and `SUPABASE_SECRET_KEY`, the fixed bucket name, and a disabled local upload flag. Set credentials there privately; never use `VITE_*` names or copy them to Vercel.
3. Run the **admin backend** (`npm.cmd run dev:api:emulator`) against `demo-petcare`; the frontend alone cannot save registration requests. Emulator document bytes are held only in the backend process and test metadata is in the emulator.
4. Run `npm.cmd run dev:maps:web:emulator`; `VITE_ADMIN_API_BASE_URL` defaults to `http://localhost:10000`.
5. Run `npm.cmd test`, `npm.cmd run test:emulators`, `npm.cmd run test:browser`, and `npm.cmd run build`. The browser script starts the demo Auth/Firestore emulators, the emulator API and Vite on loopback. The opt-in `npm.cmd --prefix admin-backend/render-api run test:supabase:integration` uses only a generated synthetic PDF, a unique test UID and cleanup limited to objects created in that run.

## Important production limits

**Do not ask actual clinics to upload sensitive identification documents.** Production uploads are hard-disabled until a malware scanner is wired and tested, consent and retention/deletion rules are approved, and the private Supabase bucket is verified. ClamAV is the practical open-source candidate, but Render Free's 512 MB memory limit is below its multi-gigabyte operating requirements; quarantine alone does not establish that a file is clean. Do not send identity documents to an unapproved scanning API. Supabase credentials belong only in the backend service. No production Base64 document data is written to Firestore; no permanent public or signed URLs are created. Emulator tests must use synthetic files only.

The versioned consent draft is captured server-side before each first upload and acceptance is audited. The displayed policy is pending legal review: draft documents are deleted after 30 days of inactivity; changes-requested documents after 60 days; rejected documents 30 days after final rejection (including the 14-day appeal period); and closed/terminated clinic documents after 90 days. Approved documents are retained while the relationship is active and require periodic necessity review, which an Admin can record and audit; the interval still needs policy approval. Legal holds, active appeals or active reviews pause deletion. Clinic audit events are retained for 365 days. The Admin dashboard provides audited hold controls and manual cleanup. No reliable free-tier scheduler is configured, so deletions are not automatic; cleanup deadlines are not operationally guaranteed until a scheduler and monitoring are provisioned.

Clinic API calls require Firebase App Check outside explicit emulator mode. Before production use, configure the frontend `VITE_RECAPTCHA_ENTERPRISE_SITE_KEY`, the matching Firebase App Check provider, and the Render CORS origin allowlist. Vercel currently hosts only the SPA; the API is separate. Its 5 MiB document limit cannot be carried into a Vercel Function unchanged because Vercel Functions limit request bodies to 4.5 MB.

The adapter includes a quarantine-and-scan interface, private-bucket verification, Admin-authenticated retrieval and audited deletion. No production scanner service or scheduled retention purge is configured. Consent and retention code is implemented but remains a draft pending privacy/legal approval; a production scanner, supported scheduler, monitoring and periodic necessity review policy remain deployment blockers. Doctor accounts, shift calendars and medical-record workflows remain Phase 2.

## Testing checklist

- Manager A submits a valid test application, sees `pending`; Manager B sees no details from A.
- The public directory remains empty until an admin approves a clinic.
- An unauthorized account cannot access the admin clinic review API or documents.
- Admin requests changes: Manager A can edit and resubmit; admin approves after reviewing documents.
- Manager A adds a bookable service; pet owner books only their own synced pet.
- Manager A accepts the request; a duplicate request for the same slot cannot also be confirmed.
- The pet owner cancels a confirmed booking; the slot becomes free.
- A suspended clinic disappears from public listings and cannot receive new bookings.
- Verify mobile layouts, English/Russian labels, backend configuration and production builds.
